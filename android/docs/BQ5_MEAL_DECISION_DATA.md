# BQ5 — Smart-result data and integration (Juan Pablo)

**BQ5:** among cooking, walking to a restaurant and ordering delivery, which available alternative
has the lowest combined estimated time and cost while prioritising food that expires within three
days?

This document covers **Person A (Juan Pablo)'s part of Issue #4**: the request and response
contract, the domain models, the repository and the use case. Person B (Natalia) owns
`MealDecisionViewModel`, the Loading / Comparison / Detail screens and the analytics events.

**The backend owns the answer.** It scores, ranks, marks the recommended alternative and writes the
explanation. This layer validates the response and passes it through unchanged: there is no scoring
formula, no sorting and no tie-breaking anywhere in the Android code.

## Request

```http
POST /api/v1/meal-decisions/compare
Authorization: Bearer <access-token>
```

```json
{
  "location": { "latitude": 4.6025, "longitude": -74.0653 },
  "campusId": "campus-001",
  "availableMinutes": 45,
  "maximumBudget": 20000,
  "dietaryPreferences": ["VEGETARIAN"],
  "includeDelivery": true,
  "requestedAt": "2026-09-17T17:30:00Z"
}
```

`location` comes from BQ4 and is always present: a device fix, or the centre of the campus the user
picked. `requestedAt` is generated by the app, in UTC. `java.time` needs API 26 and minSdk is 24, so
it is formatted with `SimpleDateFormat`.

## Response

Envelope: `recommendationId`, `alternatives`, `mainExplanation`, `supportingReasons`.
Each alternative: `type` (`COOK` / `WALK` / `ORDER`), `rank`, `score`, `recommended`,
`estimatedMinutes`, `estimatedCost`, plus `expiringIngredients` for Cook and `restaurant`
(with `walkingMinutes`, or `deliveryMinutes` and `deliveryFee`) for Walk and Order.

Every alternative field is nullable in the DTO on purpose, so one incomplete alternative is dropped
instead of failing the whole response.

## Validation

**The envelope is rejected** (`InvalidResponse`) when `recommendationId` is blank, when
`mainExplanation` is blank next to valid alternatives, or when more than one alternative is marked
recommended — Android must not choose between them.

**An alternative is skipped and counted** when its type is not one of the three supported values,
when `rank` is below 1, `score` is not finite, `recommended` is absent, or time or cost are missing
or negative; when a Cook ingredient has a blank id or name or a `remainingDays` outside 0–3; when a
Walk or Order alternative has no restaurant, a blank restaurant id or name, or is missing its
walking, delivery or fee figure; or when its type repeats one already seen.

Outcomes:

| Situation | Result |
| --- | --- |
| Every alternative valid | `Content` |
| Some valid, some skipped | `PartialContent(skippedAlternatives)` |
| Backend returned an empty list | `NoAvailableAlternatives` |
| Backend returned alternatives but none survived | `Failure(InvalidResponse)` |
| No session, or HTTP 401 | `Unauthorized` |
| Connectivity failure or HTTP 5xx | `Failure(BackendUnavailable(httpCode))` |
| Any other non-2xx | `Failure(Http(code))` |
| `availableMinutes <= 0` or negative budget | `Failure(InvalidContext)`, no request sent |

There is no cache. A recommendation depends on the time of day and on live restaurant data, so a
stale one would be misleading — unlike BQ2, which is offline-first.

## Integration contract for Natalia

```kotlin
when (val result = container.compareMealOptions(decisionContext)) { … }
```

`MealDecisionResult` maps one to one onto the required UI states; `Initial` and `Loading` belong to
the ViewModel. `MealDecision.recommended` returns the alternative the backend marked, or null when
that one had to be skipped — in which case the result is `PartialContent`, so the screen can say the
comparison is incomplete rather than promote another option.

`alternatives` is already in backend order. Render it as-is, and use `alternative.rank` and
`alternative.score` for display only. `recommendationId` is the value the
`recommendation_impression` and `recommendation_selected` events must carry.

`DecisionContext` is the input this layer needs. When `MealContext` lands with the Set Context
screen, build a `DecisionContext` from it rather than duplicating these fields.

## Validation of this change

No automated tests: the prototype is validated by compilation, lint and manual runs.

| Command | Result |
| --- | --- |
| `./gradlew :app:assembleDebug` | BUILD SUCCESSFUL |
| `./gradlew :app:lintDebug` | BUILD SUCCESSFUL, 0 errors |

**Not exercised at runtime yet.** The comparison needs a signed-in session and the BQ5 screens, and
neither exists: `InMemorySessionStorage` holds no tokens, so `compare()` returns `Unauthorized`
before any request is built, and there is no screen that calls the use case. The endpoint is also
not implemented in the NestJS backend. This path becomes testable by hand once login stores a token
and Natalia's Comparison screen calls `container.compareMealOptions`.
